# 2026-10-03

## Decisions

- Desktop shell: Electron. Terminal: node-pty + xterm.js.
- Visual language: black chalkboard, faint haze and ruling, colored chalk with one meaning per color
  (white text, yellow focus, blue info, green done, pink problem, orange question). Chalk applies only
  to the board.
- Layout: no file explorer. The board fills the window as an endless canvas; controls float at the
  top; the terminal floats at the bottom as glass so the board shows through.
- Project content is English.
- Positions are board cells `col,row` (integers, may be negative); a cell is 120 board pixels and
  the renderer zooms the board, never the cell.
- The CLI holds no logic: the command tree lives in the core, so help text and behavior have one owner.
- The CLI reads stdin only for an explicit `-` (batch). Agents' shells may keep stdin open; reading
  it implicitly could hang a command.

## Lessons

- Electron with an ESM main: a top-level `await app.whenReady()` deadlocks, because Electron fires
  `ready` only after the main module finishes evaluating. Use `app.whenReady().then(start)`.
- Electron 44 downloads its binary through its `install-electron` bin, not a postinstall that bun runs;
  `package.json` runs it as `postinstall`.
- node-pty 1.1 ships N-API prebuilds; no rebuild against Electron was needed.

- `agent/laboratory/cdp.ts`: drives the running window through DevTools (screenshot, typing into the

## Writing animation

- Fresh chalk is written, not shown: text appears character by character (~38 chars/s, capped at
  2.6s per item), steps line by line with done steps struck through after their words, flows outline
  each box then label then arrow, questions fade their buttons in after the question is written,
  the avatar's speech bubble writes itself. Moved items glide.
- Items carry `createdAt` from the core; the view animates only items younger than 1.5s when they
  first appear, so a reload never replays old writing. Reduced motion turns it all off.
- Lesson: core changes need a full app restart; reloading the window only reloads the renderer.

## Terminal rendering

- The terminal draws with the xterm WebGL renderer (`@xterm/addon-webgl`), transparent background kept;
  if the WebGL context is lost it falls back to the DOM renderer.
- The first row was cut at the top: padding sat on the host, which the fit addon does not subtract.
  Padding now sits on `.xterm` itself, which it does subtract.
- Equal margins: the terminal keeps one gutter (20px) on every side. Rows and columns are computed
  directly from the cell size (not the fit addon, which reserves a fixed scrollbar width on the right),
  and the leftover from whole cells is split evenly between opposite sides. Measured with opencode
  open: left 24, right 24, top 22, bottom 22.
- Lesson: never name an app class `.terminal`; xterm adds `terminal` to its own root element, and the
  panel's absolute positioning leaked into xterm and skewed every side.

## Terminal pin and maximize

  used by both the toolbar and the maximized terminal.

## Pinning and linking

- `board pin <col,row> <path> [--width] [--caption]`: the core copies the image (png jpg gif webp svg
  avif bmp, up to 25 MB) into the instance's asset folder; the page loads it through the private
  `board-asset:` scheme. Paths resolve against the caller's cwd, which the CLI now sends with each
  request. A pinned photo is a physical object, not chalk: white border, shadow, thumbtack, a small
  tilt around the pin point, caption in handwriting; it drops in once and the tack is pushed in.
- `board link <a> <b> [--label] [--style thread|chalk] [--color]`: links live in their own collection.
  Default style: a wool thread pin to pin when both ends are photos (sags with distance, drawn over the
  photos), a chalk arrow edge to edge otherwise (drawn under the items). Links follow items as they
  move (re-measured each frame while an item glides) and are erased with either end.
- Lesson: SVG elements have no offset box (`offsetLeft` is undefined); the first threads computed NaN
  pin points. The pin point now derives from the photo's own box.
- Item and link ids share one counter (t7 after l5, l6); `board items` lists both.

## Notes, boards per project, title bar

- `board note <col,row> <text> [--color] [--width]`: a paper note with a thumbtack, written in ink;
  the color is the paper's (yellow by default). Photos and notes are both "pinned kinds"; a link
  between two pinned things defaults to a thread.
- `board pin` also takes an http(s) URL: downloaded with a 15s timeout, must be an image type, 25 MB
  at most. Requests carry a User-Agent built from the project name and version (some hosts refuse
  anonymous requests).
- Boards are kept per project folder, in the app's data folder (`<userData>/boards/<folder>-<hash>/`:
  board.json, assets/, project.json naming the path), never inside the project. Saved 0.4s after each
  change (atomic write) and on quit; restored at start with ids continuing; unused assets pruned.
  Erased ghosts and the avatar's speech bubble are not kept.
- Title bar: app name / project / git branch. The project name is the git top-level folder's name (or
  the folder's); the branch is watched (git dir HEAD changes, plus a 10s poll) and shows the short
  commit when detached. Not a git repo: no branch.
- Verified on a git project (sequoia, then its test board deleted): title "More Space / sequoia / main",
  notes and threads drawn, image from a URL pinned, board restored after a restart, project untouched
  (`git status` clean).
- Title bar fix: the branch used the monospace face at a smaller size and sat higher than the other
  words. All parts now share one face and size and are centered on one line with flex; measured
  centers: project 16.5, branch text 16.5, branch icon 16.5.
